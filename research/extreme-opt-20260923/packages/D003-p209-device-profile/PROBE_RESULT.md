Every device source was verified identical to P209; only the host collector and

Cluster 0 dominant DMA durations: 25440, 25804, 25344 cycles. Remaining task
windows after that DMA: 11276, 9849, 11196. Historical D002/P166 values were
10419, 10890, 11880. These are different sessions, not a paired performance proof.

The first TuExec after dominant DMA lasts 3409/3413/3403 cycles, consistent with
P166's 3405/3405/3399 contraction. The final TuExec lasts 516 cycles in all three
P209 runs versus 520 in D002. Neither indicates a large compute reduction.
Intervening DMA and TuExec ordering differs, providing a concrete reason to
investigate operand readiness and synchronization on the P209 base.

Priority 1: obtain the P209 instruction schedule and correlate changed Sub passes
with RMS/scale/sw/residual readiness. Test whether allocation/reuse dependencies
delay the first RMS pass. P166's schedule contains DramReuse and ExplicitSync;
trace Cluster spans alone cannot identify a particular barrier or prove it is
removable. Do not add nested span durations as independent costs.

Priority 2: remove mean DM materialization only with a legal scalar consumer.
SDK 0.8.1 intra pipeline orders Fp before IntraSliceReduce, then FpDiv, so P076's
reduce-then-sqrt fusion cannot be reused. A VRF handoff needs a valid input stream
and matching slice geometry; it is a hypothesis, not an implemented solution.

P209 remains an open development base. No promotion or architecture-family
rejection follows from these diagnostic timings. The earlier 36.2K estimate
assumed an unchanged tail; it is not a hardware lower bound.
